# Instructor preflight and classroom checkpoints

Use with the [instructor guide](../instructor-guide.md), [setup guide](../setup-guide.md), [website skills](../skill-guide.md), [game skills](../game-skills-guide.md), and [student workbook](../handouts/student-workbook.md).

The class has **360 teaching minutes** and two projects: a simple website, then a small browser game. Breaks and lunch are additional. Each learner uses their favorite chatbot and separate folders, GitHub repositories, and Vercel projects for the two builds. Native skill installation is optional; pasting or attaching the relevant instructions supports the portable route.

## Prepare before class

- Send the setup guide, the laptop/browser requirement, and the account-access checklist. Ask learners to verify they can receive runnable files from their preferred chatbot.
- Choose one primary demonstration route. Keep the portable file route ready even when demonstrating a connected workspace.
- Prepare a tested website checkpoint and a playable checkpoint for every game recipe you offer. Record the file version and tests. This repository's instructions are not a substitute for tested starter applications.
- Rehearse copying or downloading files, saving plain text, extracting a ZIP, opening `index.html`, and uploading the files rather than the archive.
- Prepare two visibly distinct folders and repositories, such as `my-first-site` and `my-first-game`. Recheck project identity at each upload and deployment.
- Choose a few Arcade examples that show clear instructions, controls, a result, and replay. Treat the more complex examples as future possibilities.
- Have one short heading change ready to show a saved version, branch, proposed change, preview, and release. Keep the explanation connected to the visible outcome.
- Keep a setup-blocker list. After five minutes on an individual problem, use a tested checkpoint or partner and return to the account issue later.

## Checkpoints during the 360 teaching minutes

Elapsed times exclude lunch and breaks. The [instructor guide](../instructor-guide.md) contains the teaching detail.

| Elapsed | Minutes | Checkpoint and evidence | If a learner is behind |
| --- | ---: | --- | --- |
| 0:00–0:30 | 30 | Learner can connect discover, define, design/plan, build, test, release, and maintain to a website or game example | Reuse the same example and ask for one observable test |
| 0:30–1:00 | 30 | Correct learner-owned website repo identified; runnable-file or connected-workspace route verified | Use a checkpoint or partner; record the access blocker |
| 1:00–2:30 | 90 | Website brief, working files, test report, and release record; main action checked at actual URL or blocker recorded | Reduce to one page and one meaningful link |
| 2:30–2:45 | 15 | Learner selects a small game pattern and theme | Offer a prepared puzzle, one-button, or paddle recipe |
| 2:45–3:05 | 20 | Partner can explain goal, controls, score, round end, and restart from the written rules | Remove extra mechanics; keep one short round |
| 3:05–4:10 | 65 | Player completes start, play, result, and restart with plain visuals | Use the playable checkpoint; defer decoration |
| 4:10–4:40 | 30 | Controls, score, result, and Play again are understandable on the intended screens | Fix legibility and instructions before optional effects |
| 4:40–5:20 | 40 | Uncoached partner observations recorded; largest issue repaired and retested | Fix one issue and label remaining failures honestly |
| 5:20–5:45 | 25 | Separate game repository/project verified; deployed round and restart checked or exact blocker saved | Retain runnable files and complete the release record |
| 5:45–6:00 | 15 | Paired demonstration and two-project handoff with versions, evidence, limits, and next action | Demonstrate local files when deployment is blocked |

Total: **360 minutes**. The website block contains approximately 15 minutes of definition, 50 of building/refinement, and 25 of checking/publication.

## Before each build and release

Ask learners to name the current project and show its destination. A new game must not replace the website files. Have them show the brief and expected behavior before asking the chatbot to change anything.

Before publishing, learners identify the repository, Vercel project, version, and intended audience. Explain that the first Vercel deployment is production and that subsequent production-branch changes may deploy automatically. Confirm the specific publication, then check the actual resulting URL. A private repository does not establish private access to the website.

For the website, observe the main action and phone layout. For the game, observe a full round, result, and repeated restart; also check the supported keyboard and touch controls. Record the exact device and whether a real phone was used. A resized browser is useful evidence but does not prove touch-device behavior.

## Review the evidence

Accept **Passed** only when the stated behavior was observed on the recorded version. Use **Failed** for a tried check that did not match the expectation and **Not tested** for an untried check. Keep local-file, preview, and published-URL results distinct.

Use a real partner for the first-time-player test. A chatbot asked to take several review roles provides several perspectives, not several independent reviewers. Ask for two minutes of uncoached play before discussing improvements.

A green deployment indicator is not the acceptance test. If a project cannot be deployed or checked, retain its working files, version, precise blocker, and next action. Avoid calling an unverified URL a completed project.

## Close the day

Have each learner demonstrate the website's main action and the game's round/restart loop, identify both saved projects, and complete the handoff template. Check that they know where their files and records are and can describe one small next improvement plus how they will verify it.

Record recurring setup problems and confusing instructions for the next rehearsal. Keep incomplete account issues separate from what the learner successfully built and tested.

## Self-guided materials and AI access

Before distributing the course, decide how learners will receive the private repository or a course copy. Test the authorized-repository route, the single-file AI-COURSE-PACK.md upload, and the pasted-lesson fallback in the actual supported student surfaces. The class instructions do not grant repository access.

Use [START-HERE.md](../START-HERE.md) as the student landing page. Open the [illustrated guide](../guides/participant-guide.pdf), verify its links, and introduce [troubleshooting](../docs/troubleshooting.md). Demonstrate a cold restart using project-state.md and the actual files. Offer [multiple agents](../docs/multiple-agents.md) only when learners have a working first version; it is not an extra required block in the 360-minute schedule.
